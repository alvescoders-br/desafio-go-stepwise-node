# Phase C: Verify Build, Generate README & AGENTS.md

## Context Contract
- **Inputs:** IMPL_INDEX with all files_touched, `source_path`, and `project_root`; source directory on disk
- **Outputs:** README.md at `{IMPL_INDEX.project_root}`, AGENTS.md at `{IMPL_INDEX.project_root}` (final phase only), build verification log
- **Carries Forward:** IMPL_INDEX with build_commands_discovered, tech_stack_detected
- **Flush After:** File scan results, build output
- **Dependency:** Phase B must be COMPLETE (all files written to disk)

> ⚠️ **Phase C has FIVE steps, not three.** Build passing does NOT mean Phase C is done.
> The required sequence is: Tech Stack Discovery → Tool Inventory → Build Verification → README.md → AGENTS.md (final phase) → Completion Gate → Phase D.
> Jumping to Phase D after tests pass — without Step 5 and the Completion Gate — is the most common failure mode in this skill.

---

## Purpose

This phase exists because the most common failure mode is: code is generated,
marked COMPLETE, but doesn't compile or run. The human then enters a repair
loop that takes 5-7 iterations. This phase catches those issues BEFORE the
human sees the code.

**This phase is MANDATORY. It cannot be skipped.**

## Step 1: Discover Tech Stack (Framework-Agnostic)

```
The skill does NOT hardcode any framework. Instead, it discovers what was
generated by scanning the files on disk.

SCAN {IMPL_INDEX.project_root} recursively for known build/config files:

detected = {
  languages: [],
  build_tools: [],
  frameworks: [],
  services: [],
  build_commands: [],
  entry_points: [],
  config_files: [],
  container_orchestration: null
}

## Language & Build Tool Detection
FOR EACH file found by scanning the source directory:

  IF pom.xml found:
    detected.languages += "Java"
    detected.build_tools += "Maven"
    EXTRACT java.version from pom.xml properties
    EXTRACT spring-boot version from parent (if present)
    ADD service: { name: dirname, type: "maven", pom_path: path }
    detected.build_commands += "mvn -f {pom_path} compile"
    detected.build_commands += "mvn -f {pom_path} test"

  IF build.gradle or build.gradle.kts found:
    detected.languages += "Java" or "Kotlin"
    detected.build_tools += "Gradle"
    ADD service: { name: dirname, type: "gradle", build_path: path }
    detected.build_commands += "gradle -p {dir} build"

  IF package.json found:
    detected.languages += "JavaScript/TypeScript"
    detected.build_tools += "npm"
    READ package.json → extract scripts section
    IF scripts.build exists → detected.build_commands += "npm run build"
    IF scripts.test exists → detected.build_commands += "npm run test"
    IF scripts["type-check"] → detected.build_commands += "npm run type-check"
    CHECK for tsconfig.json in same directory
    ADD service: { name: dirname, type: "npm", pkg_path: path }

  IF requirements.txt or pyproject.toml or setup.py found:
    detected.languages += "Python"
    detected.build_tools += "pip" or "poetry"
    detected.build_commands += "python -m py_compile {main_file}"

  IF go.mod found:
    detected.languages += "Go"
    detected.build_tools += "go"
    detected.build_commands += "go build ./..."

  IF Cargo.toml found:
    detected.languages += "Rust"
    detected.build_tools += "cargo"
    detected.build_commands += "cargo check"

  IF Makefile found:
    detected.build_tools += "make"
    detected.build_commands += "make"

  IF Dockerfile found:
    detected.container_orchestration = "docker"
    ADD entry_point: { type: "dockerfile", path: path, service: dirname }

  IF docker-compose.yml or docker-compose.yaml or compose.yml found:
    detected.container_orchestration = "docker-compose"
    PARSE compose file:
      FOR EACH service with "build:" context:
        ADD to detected.services if not already present
        RECORD: { name, build_context, expected_dockerfile_path }

  IF Vagrantfile, serverless.yml, fly.toml, etc. found:
    ADD to detected.config_files

UPDATE IMPL_INDEX:
  tech_stack_detected = detected
  build_commands_discovered = detected.build_commands

LOG: "Tech stack discovered: {languages}, {build_tools}. Services: {count}."
```

## Step 2: Scaffolding Completeness Gate

```
This gate verifies that all cross-file references resolve.
It is FRAMEWORK-AGNOSTIC — it reads what exists and checks consistency.

ERRORS = []

## 2a: Docker Compose Build Context Check
IF docker-compose file exists:
  FOR EACH service with "build:" directive:
    RESOLVE: build_context_path + "/Dockerfile"
    IF Dockerfile does NOT exist at that path:
      ERRORS += "MISSING_FILE: Dockerfile required at {path} for service {name}"

## 2b: TypeScript / JavaScript Project Check
FOR EACH directory containing package.json:
  IF tsconfig.json exists:
    READ tsconfig.json
    IF "references" field contains paths → verify each referenced file exists
    IF "include" or "files" → verify they resolve
    Common missing file: tsconfig.node.json (Vite projects)
      IF tsconfig.json references tsconfig.node.json AND it doesn't exist:
        ERRORS += "MISSING_FILE: tsconfig.node.json referenced by tsconfig.json"

  IF package.json scripts.build contains "vite" or "vite build":
    VERIFY index.html exists at project root (not in public/, not in src/)
    IF NOT exists:
      ERRORS += "MISSING_FILE: index.html (Vite entry point) at {project_root}"
    VERIFY src/main.tsx or src/main.ts or src/index.tsx or src/index.ts exists
    IF NOT exists:
      ERRORS += "MISSING_FILE: Entry point (main.tsx/index.tsx) in src/"

  IF package.json scripts.build contains "next":
    VERIFY pages/ or app/ directory exists

## 2c: Java / Maven Project Check
FOR EACH directory containing pom.xml:
  READ pom.xml
  IF parent POM defines a version BUT a dependency uses ${variable}
    that is NOT defined in properties:
      ERRORS += "CONFIG_ERROR: Unresolved property {variable} in {pom_path}"

  IF flyway dependency exists:
    Verify flyway-core and any flyway-database-* dependencies have
    compatible versions (either BOM-managed or explicit)

  VERIFY main Application class exists:
    Scan src/main/java/ for @SpringBootApplication or public static void main
    IF NOT found:
      ERRORS += "MISSING_FILE: No application entry point in {service}"

  IF Dockerfile NOT exists AND docker-compose references this service:
    ERRORS += "MISSING_FILE: Dockerfile for {service}"

## 2d: General Cross-Reference Check
FOR EACH file in IMPL_INDEX.files_touched:
  Quick-scan for import/require/include statements
  FOR EACH referenced module/file:
    IF it references a local file (not a library):
      Verify that file exists on disk OR is in IMPL_INDEX.files_touched
      IF NOT found:
        ERRORS += "MISSING_REF: {file} imports {ref} which does not exist"

## 2e: Comment Syntax Check
FOR EACH file in IMPL_INDEX.files_touched:
  READ first 3 lines of the file
  CHECK: does the file use incorrect comment syntax?
    - Dockerfile starting with <!-- → ERROR
    - .java file starting with # comment → ERROR
    - .sql file starting with // → ERROR
    - .yml file starting with <!-- → ERROR
  IF incorrect:
    ERRORS += "SYNTAX_ERROR: {file} uses wrong comment syntax"

## 2f: HTTP Status Code Verification (REST APIs)
IF implementation includes REST controller/endpoint files:
  FOR EACH endpoint in the plan's interface contracts or AC:
    CHECK error handling paths:
      - Invalid input data / malformed request → must return 400 (Bad Request)
      - FK reference to non-existent resource → must return 400 (Bad Request), NOT 404
      - Resource identified by path param not found (GET /x/{id}) → must return 404 (Not Found)
      - Duplicate unique constraint violation → must return 409 (Conflict)
      - Business rule violation → must return 422 (Unprocessable Entity) or 400
    IF wrong status code detected (e.g., throwing NotFoundException for invalid input):
      ERRORS += "STATUS_CODE: {endpoint} returns {actual} for {scenario}, spec requires {expected}"
  CHECK for hardcoded environment config:
    - spring.profiles.active set in application.yml (should be externalized)
    - Hardcoded URLs, ports, or hostnames
    IF found:
      ERRORS += "CONFIG_HARDCODE: {file} has hardcoded environment value: {value}"

## Process Errors
IF ERRORS is not empty:
  LOG: "Scaffolding gate found {count} issues."
  FOR EACH error:
    LOG error
    ATTEMPT AUTO-FIX:
      IF MISSING_FILE → Generate the missing file
      IF CONFIG_ERROR → Fix the configuration
      IF SYNTAX_ERROR → Rewrite first lines with correct syntax
      IF MISSING_REF → Check if it's a library import (OK) or local (fix needed)
    
    WRITE fix to disk — MANDATORY TOOL CALL
    UPDATE IMPL_INDEX.files_touched with new/modified file
    LOG: "AUTO-FIX: {description}"

  RE-RUN scaffolding gate (max 2 re-runs)
  IF errors persist after 2 re-runs → log remaining as blockers

ELSE:
  LOG: "Scaffolding gate passed. All references resolve."
```

## Step 2b: Plan Adherence Verification

```
## Before proceeding, verify implementation matches the plan.
## Catches the failure mode where features are silently dropped
## and marked as "known limitations" without attempting them.

READ phase document for current ACTIVE_PHASE

FOR EACH planned_item in phase.files_to_create + phase.files_to_modify:
  VERIFY: File exists at expected path
  VERIFY: File contains the planned functionality (not a stub or placeholder)
  IF missing or incomplete:
    IF planned approach was attempted and documented as technically infeasible
       (evidence in IMPL_INDEX.blockers):
      STATUS = ACCEPTABLE — "Known limitation" with evidence of attempt
    ELSE:
      STATUS = INCOMPLETE — must implement before proceeding
      LOG: "PLAN ADHERENCE FAIL: {planned_item} not implemented, no documented blocker"

FOR EACH acceptance_criterion assigned to this phase:
  VERIFY: Corresponding implementation exists with code reference
  IF not implemented:
    LOG: "PLAN ADHERENCE FAIL: AC {ac_id} not implemented"

## Enforcement
IF any PLAN ADHERENCE FAIL:
  LOG: "Plan adherence check failed. Returning to Phase B for completion."
  UPDATE IMPL_INDEX.plan_adherence_returns += 1
  IF IMPL_INDEX.plan_adherence_returns > 2:
    LOG: "Max plan adherence returns (2) exceeded. Escalating as blocker."
    ADD remaining failures to IMPL_INDEX.blockers
    ## REC-001: record the verdict so the Completion Gate can enforce it.
    RECORD IMPL_INDEX.validations["plan_adherence"] = { verdict: "FAIL", evidence: <unresolved items> }
  ELSE:
    GOTO Phase B with focus on missing items only
ELSE:
  RECORD IMPL_INDEX.validations["plan_adherence"] = { verdict: "PASS", evidence: "all planned files + ACs present" }
```

## Step 2c: AC Test Coverage Matrix

```
## Verify that every Acceptance Criterion (AC) from the task description
## has at least one corresponding test. Catches the failure mode where
## source code implements all ACs but test coverage is incomplete —
## which the plan adherence check (Step 2b) does not catch.

IF IMPL_INDEX.task_description_path exists AND is not empty:
  READ task_description_path file

  ## Extract AC identifiers using fuzzy matching (format varies by project):
  ##   - Explicit IDs: AC-01, AC-02, AC-1, AC-2
  ##   - Story-scoped: S1/F1, S2/F3, US-01-AC-03
  ##   - Numbered lists under "Acceptance Criteria" heading
  ##   - Gherkin scenarios (Scenario: / Scenario Outline:)
  ## If no structured AC identifiers found, extract numbered items from
  ## sections titled "Acceptance Criteria", "AC", or "Verification Criteria"

  ACCEPTANCE_CRITERIA = extract_ac_identifiers(task_description)

  IF ACCEPTANCE_CRITERIA is empty:
    LOG: "No structured ACs found in task description. Skipping coverage matrix."
    SKIP to Step 3

  coverage_map = {}
  UNCOVERED = []

  FOR EACH ac in ACCEPTANCE_CRITERIA:
    COVERED = false

    ## Search test files for references to this AC
    FOR EACH test_file in IMPL_INDEX.files_touched where file is a test:
      SEARCH test_file content for:
        - Exact AC ID string (e.g., "AC-01", "S1/F1")
        - AC description keywords (first 5-8 significant words)
        - Test method name containing the AC ID (e.g., "testAC01_", "should_verify_ac01")
      IF any match found:
        coverage_map[ac.id] = { test_file: test_file.path, status: "COVERED" }
        COVERED = true
        BREAK

    IF NOT COVERED:
      coverage_map[ac.id] = { status: "UNCOVERED" }
      UNCOVERED += ac

  LOG: "AC Coverage: {covered_count}/{total_count} ACs have test coverage."

  ## FTC augmentation (only when test_cases_path was supplied):
  ## The plan's testing_strategy.test_case_id ties each planned test to a precise
  ## upstream FTC — finer-grained and more authoritative than fuzzy AC matching.
  ## Add those FTC ids to the coverage set so the matrix is FTC-exact.
  IF test_cases_path was supplied:
    FTC_EXPECTED = [ row.test_case_id for row in PLAN.testing_strategy
                    where row.test_case_id is an FTC id
                    AND NOT (row.type == "e2e" AND row.covered_by == "qe-web-automation") ]
    FOR EACH ftc_id in FTC_EXPECTED:
      IF no test file references ftc_id (comment or test name):
        UNCOVERED += ftc_id   ## generation below will create it
    ## When generating a missing FTC-anchored test, its assertions MUST reflect the
    ## cited FTC's Gherkin Then clauses (load that one suite file, then flush it) —
    ## do NOT invent assertions that contradict the FTC.
    LOG: "FTC Coverage: {covered}/{len(FTC_EXPECTED)} in-scope FTC-anchored tests present."

  ## Generate missing tests for uncovered ACs
  IF UNCOVERED is not empty:
    LOG: "Generating tests for {count} uncovered ACs..."
    FOR EACH ac in UNCOVERED:
      GENERATE test for ac using:
        - AC description as the test specification
        - Existing test files as pattern reference (naming, imports, assertions)
        - Same test framework detected in Step 1 (JUnit, Jest, pytest, etc.)
      WRITE test file to disk
      UPDATE IMPL_INDEX.files_touched with new test file
      UPDATE coverage_map[ac.id] = { test_file: new_file.path, status: "GENERATED" }
      LOG: "Generated test for {ac.id}: {new_file.path}"

    ## Re-verify: all ACs should now be covered
    STILL_UNCOVERED = [ac for ac in coverage_map where status == "UNCOVERED"]
    IF STILL_UNCOVERED is not empty:
      LOG: "WARNING: {count} ACs still uncovered after generation attempt."
      FOR EACH ac in STILL_UNCOVERED:
        LOG: "  - {ac.id}: {ac.description}"
      ADD to IMPL_INDEX.blockers: "AC coverage gaps remain: {list}"
      RECORD IMPL_INDEX.validations["ac_coverage"] = { verdict: "FAIL", evidence: STILL_UNCOVERED }   ## REC-001
    ELSE:
      RECORD IMPL_INDEX.validations["ac_coverage"] = { verdict: "PASS", evidence: "{covered}/{total} ACs covered" }
  ELSE:
    RECORD IMPL_INDEX.validations["ac_coverage"] = { verdict: "PASS", evidence: "all ACs already covered, none generated" }

  ## Store matrix for downstream use (code-review can consume this)
  UPDATE IMPL_INDEX.ac_coverage_matrix = coverage_map

ELSE:
  LOG: "No task_description_path available. Skipping AC coverage matrix."
  RECORD IMPL_INDEX.validations["ac_coverage"] = { verdict: "N/A", evidence: "no task_description ACs" }   ## REC-001
```

## Step 2d: Plan-Spec Assertion Verification

```
## Verify that every test written in this phase includes ALL assertions
## specified by the PLAN-SPEC step that required it. Catches the failure mode
## where a test exists (passes Step 2c) but omits specific assertions the plan
## mandated — causing plan-to-code drift that only the code-review catches later.

IF plan is available AND phase has test files:

  FOR EACH test_file in files_touched WHERE test_file is not null:
    LOCATE the PLAN-SPEC step that required this test
    EXTRACT expected_assertions from that plan step
      (e.g., field names to assert, status codes to check, mock return values)

    READ test_file
    FOR EACH expected_assertion in expected_assertions:
      VERIFY assertion is present in test code
      IF MISSING:
        LOG: "PLAN DRIFT: {test_file} missing assertion for '{expected_assertion}' required by plan step {step_id}"
        ADD the missing assertion to the test file
        FLUSH test file to disk

  IF any assertions were added:
    LOG: "Plan-spec assertion verification: {N} missing assertions added to {M} test files."
  ELSE:
    LOG: "Plan-spec assertion verification: all tests match plan requirements."

ELSE:
  LOG: "No plan or no test files in this phase. Skipping assertion verification."
```

## Phase C Completion Gate (MANDATORY — DO NOT PROCEED WITHOUT PASSING)

```
## This gate verifies that all Phase C artifacts exist on disk before
## allowing Phase D to execute. It catches the failure mode where
## the agent skips documentation steps after build verification passes.

GATE_ERRORS = []

## Check 1: Tool verification ran (or was explicitly skipped)
IF IMPL_INDEX.tool_results is empty AND bash tool IS available:
  GATE_ERRORS += "MISSING: Tool verification — Step 3 was skipped. Run it NOW."

## Check 2: README.md
VERIFY README.md exists at {IMPL_INDEX.project_root}/README.md
IF NOT exists:
  GATE_ERRORS += "MISSING: README.md — Step 4 was skipped. Generate it NOW."

## Check 3: AGENTS.md (final phase only)
CHECK: Are there remaining PENDING phases in IMPL_INDEX after this one?
IF NO (this is the final phase):
  VERIFY AGENTS.md exists at {IMPL_INDEX.project_root}/AGENTS.md
  IF NOT exists:
    GATE_ERRORS += "MISSING: AGENTS.md — Step 5 was skipped. Generate it NOW."

IF GATE_ERRORS is not empty:
  LOG: "Phase C Completion Gate FAILED. Missing artifacts:"
  FOR EACH error in GATE_ERRORS:
    LOG: "  - {error}"
  LOG: "RETURNING to the skipped steps. Do NOT proceed to Phase D."
  ## Execute the missing steps NOW, then re-run this gate.
  ## LOOP-SAFE: each missing step writes ONE file (README/AGENTS) and is satisfied
  ## on the next pass — this is a generate-once fix, NOT a re-run of tests/build.
  GOTO the first missing step

## ──────────────────────────────────────────────────────────
## Check 4: Build / Test outcome gate (TERMINAL — never loops)  [CAL-INF-001]
## ──────────────────────────────────────────────────────────
## A recorded build/test FAIL must BLOCK `complete`. Before this check existed,
## the run fell through to COMPLETED_WITH_WARNINGS and only the human caught it.
##
## ⛔ This check NEVER does GOTO back to Step 3 / tool verification. The
## self-correction budget (MAX_ATTEMPTS = 3 in phase-c-tools.md) is already spent.
## Re-running here would be the infinite loop this design forbids. Instead it sets
## a forced Phase-C outcome that Phase D converts into a terminal status, and the
## ONLY further iteration is the orchestrator-driven REPAIR cycle (externally
## bounded by repair_log / the orchestrator's own attempt cap).

READ IMPL_INDEX.build_gate (default "PASS"), IMPL_INDEX.test_gate (default "PASS")

IF build_gate == "FAIL_GENUINE" OR test_gate == "FAIL_GENUINE":
  SET IMPL_INDEX.phase_c_outcome = "FAILED"
  LOG: "Phase C Completion Gate: BLOCKING — unresolved {build/test} failure after 3 self-correction attempts. Routing to Phase D as FAILED (→ REPAIR). NOT looping back to tool verification."

ELSE IF build_gate == "FAIL_ENVIRONMENTAL" OR test_gate == "FAIL_ENVIRONMENTAL":
  SET IMPL_INDEX.phase_c_outcome = "BLOCKED"
  LOG: "Phase C Completion Gate: BLOCKING — environmental build/test failure (runner could not execute). Routing to Phase D as BLOCKED (→ human). NOT looping."

ELSE:
  SET IMPL_INDEX.phase_c_outcome = "PASS"

## ──────────────────────────────────────────────────────────
## Check 5: Required-validations evidence gate (TERMINAL — never loops)  [REC-001]
## ──────────────────────────────────────────────────────────
## The Pre-Completion checks (plan adherence, AC coverage, plan-file coverage,
## artifact fidelity, TDAD) used to be advisory — the agent could declare COMPLETED
## without provably running them, which is why implementation-validation rejected a
## majority first-pass for Incomplete / Wrong_Format. This gate makes the EVIDENCE
## mandatory: each required check must have a recorded verdict, and an unresolved
## FAIL self-fails the run BEFORE the human gate.
##
## ⛔ LOOP-SAFE: this gate does NOT re-run any Phase C step and never GOTOs back.
## When a verdict is absent it is DERIVED from state ALREADY in IMPL_INDEX
## (plan_adherence_returns, plan_file_coverage, ac_coverage_matrix, deviations,
## blockers, tdad_compliance) — a read, not a re-execution. Evaluated exactly once.

REQUIRED = ["plan_adherence", "plan_file_coverage", "ac_coverage", "artifact_fidelity"]
IF tdad_mode enabled: REQUIRED += "tdad_compliance"

FOR EACH name IN REQUIRED:
  IF IMPL_INDEX.validations[name].verdict is absent:
    ## Derive from existing state only — do NOT re-run the step.
    DERIVE verdict (PASS | FAIL | N/A with reason) from:

## Diff-Based Verification (mandatory across all Phase C steps)

When Phase C needs to verify what the just-completed Phase B actually changed,
prefer cheap diff signals over re-reading large files:

- `git -C {source_path} diff --stat HEAD~1..HEAD` — what changed in this phase's wip-commit.
- `git -C {source_path} diff HEAD~1..HEAD -- <path>` — full diff for a single file.
- `wc -l <path>` — sanity-check on file size after edits.
- `grep -n` of the changed region for spot-checks.

**Forbidden:** re-reading any file >300 lines in full to "confirm" the edit
that Phase B already wrote. Trust the Edit tool's success indicator and the
diff signals above. Only re-read in full if a build/test failure in Step 3
disagrees with what the diff says — and even then, target the failing region,
not the whole file. Re-reading large files in Phase C was the dominant token
sink in the LAC-Android calibration run.

If the diff signals show that a file's line count collapsed or `--stat` shows
"+N -N" matching the old size (i.e., the file was effectively replaced), treat
that as an integrity break: read `references/recovery-protocol.md` and follow
the protocol. Do NOT proceed with verification of a wiped file's "build."
